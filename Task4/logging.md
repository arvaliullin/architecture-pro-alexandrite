# Архитектурное решение по логированию

## 1. Системы для сбора логов, события INFO и уровни логирования

Логи собираются из бэкенд-сервисов, брокера и хранилищ (выделены зеленой рамкой на [c4-logging.drawio](./c4-logging.drawio)). Веб-интерфейсы (`Онлайн-магазин`, `CRM`, `MES`) не пишут системные логи напрямую - ошибки клиентских запросов фиксируются на стороне API.

Все сервисы пишут структурированный JSON в `stdout` с общими полями корреляции: `timestamp` (UTC), `level`, `service`, `trace_id`, `order_id`.

### Необходимые события уровня INFO

| Компонент | Событие | Специфичные поля |
| --------- | ------- | ---------------- |
| `Shop API` | Создание, изменение статуса или отмена заказа | `customer_id`, `status_from`, `status_to` |
| `Shop API` | Загрузка или генерация 3D-файла | `customer_id`, `file_key`, `file_size_bytes` |
| `CRM API` | Подтверждение производства (`MANUFACTURING_APPROVED`), смена статуса, закрытие (`CLOSED`) | `customer_id`/`partner_id`, `seller_id`, `status_from`, `status_to` |
| `CRM API` | Публикация и прием сообщений `RabbitMQ` | `mq.queue`, `mq.message_id`, `direction` (`pub`/`sub`) |
| `MES API` | Прием B2B-заказа (`API user`) | `partner_id`, `endpoint`, `http.status_code` |
| `MES API` | Старт и завершение расчета стоимости 3D-модели | `model.polygons`, `duration_ms`, `price` |
| `MES API` | Назначение на оператора и смена статуса (`MANUFACTURING_STARTED` -> `MANUFACTURING_COMPLETED`) | `operator_id`, `status_from`, `status_to` |
| `MES API` | Публикация и прием сообщений `RabbitMQ` | `mq.queue`, `mq.message_id`, `direction` |
| `RabbitMQ` | Подключение/отключение потребителей, роутинг в DLQ | `vhost`, `queue`, `consumer_tag`, `event` |
| `Shop DB` / `MES DB` | Медленные запросы (slow query log), deadlock, смена ролей | `db_name`, `duration_ms`, `query_fingerprint` |
| `S3` | Операции записи, чтения и удаления 3D-файлов (access log) | `bucket`, `object_key`, `operation`, `http.status_code`, `bytes` |

### Другие уровни логирования

| Уровень | В prod | Когда используется |
| ------- | ------ | ------------------ |
| `FATAL` | Всегда | Падение процесса, ошибка конфигурации, невозможность старта |
| `ERROR` | Всегда | 5xx-ошибки, сбои БД/`S3`/`RabbitMQ`, падение 3D-расчета, невалидные сообщения |
| `WARN` | Всегда | Ретраи, долгий 3D-расчет (> 15 мин), медленный SQL, 4xx/rate-limit, рост очереди |
| `DEBUG` | Выключен | Детали расчета 3D и локальная диагностика; включается временно на конкретном сервисе при инциденте |
| `TRACE` | Запрещен | Не используется из-за нагрузки на CPU/диск и риска утечки данных |

## 2. Мотивация

Сейчас инциденты разбираются со слов клиентов, а поддержка и разработка тратят часы на ручной поиск причин. Централизованное логирование по `order_id` и `trace_id` дает объективную хронологию каждого заказа и разгружает команду.

| Метрика | Тип | Ожидаемый эффект |
| ------- | --- | ---------------- |
| MTTR по инцидентам с заказами | Техническая | Локализация причины за минуты вместо часов/дней |
| Доля тикетов, закрытых без эскалации в разработку | Техническая | Поддержка проверяет историю заказа сама в `OpenSearch Dashboards` |
| Доля недиагностированных сбоев и потерянных сообщений | Техническая | Фиксация всех `ERROR`/`WARN` и DLQ исключает "немые" потери |
| Доля просроченных (> 3 недель) и потерянных заказов | Бизнес | Быстрое обнаружение зависаний снижает срывы сроков |
| Скорость ответа B2C и удержание партнеров B2B | Бизнес | Точные статусы для клиентов и проактивное исправление сбоев B2B API |

## 3. Приоритетность внедрения логирования и трейсинга

Из-за ограниченного ресурса команды (в `MES` один C#-разработчик) логирование и трейсинг внедряются поэтапно:

| Этап | Системы | Обоснование |
| ---- | ------- | ----------- |
| 1 | `MES API`, `RabbitMQ`, `CRM API` | Главные источники просрочек, пропажи статусов и жалоб B2B; JSON-логи (`Serilog`, `Logback`) и автоинструментация OpenTelemetry дают максимум эффекта при минимуме доработок в `MES` |
| 2 | `Shop API`, `Shop DB`, `MES DB` | Закрывает вход B2C-заказов (`INITIATED` -> `SUBMITTED`), связывает общую `Shop DB` по `order_id`/`trace_id`, выявляет медленный SQL |
| 3 | `S3` (access-логи) | Ошибки `S3` редки и частично видны в `Shop API` и `MES API`; аудит хранилища подключается последним |

## 4. Предлагаемое решение

### 4.1 Технологии, компоненты и доработки

| Компонент | Технология | Роль и доработки |
| --------- | ---------- | ---------------- |
| Приложения | `Logback` JSON (`Shop API`, `CRM API`), `Serilog` JSON (`MES API`) | Перевод на JSON в `stdout` с `trace_id`, `order_id` и бизнес-полями |
| Сборщик на узлах | `Fluent Bit` | Агент на EC2-узлах приложений и `RabbitMQ`: сбор `stdout`/файлов, буфер на диск, отправка по TLS |
| Агрегатор | `Logstash` | Прием потоков от `Fluent Bit`, `PostgreSQL` и `S3`, нормализация, маскирование ПДн, маршрутизация |
| Хранилище | `Managed OpenSearch` (Yandex Cloud) | Индексация, полнотекстовый поиск, управление жизненным циклом индексов (ISM); единое хранилище с трейсами |
| UI и анализ | `OpenSearch Dashboards` | Поиск по `order_id`/`trace_id`, дашборды, `Alerting` и `Anomaly Detection` |
| Оповещения | `Система оповещений` (Slack/Telegram/Email) | Доставка алертов дежурным инженерам и поддержке |

Схема C4 с источниками логов, новыми компонентами и связями: [c4-logging.drawio](./c4-logging.drawio).

### 4.2 Политика безопасности

| Контур | Мера защиты |
| ------ | ----------- |
| Данные в коде | Запрет логирования ПДн (ФИО, контакты, адреса), платежных данных, паролей, токенов и 3D-файлов; только внутренние `customer_id`, `partner_id`, `order_id` |
| Маскирование | Фильтры в `Logstash` (regex на email, телефоны, заголовки `Authorization`/`Cookie`) как вторая линия защиты |
| Периметр и доступ | Вся инфраструктура логов во внутренней сети; вход в `OpenSearch Dashboards` через VPN + SSO/OIDC + RBAC (`Поддержка` - только бизнес-логи `INFO`/`WARN`; `Разработка` - индексы своих сервисов; `DevOps`/`ИБ` - администрирование и аудит) |
| Транспорт и хранение | TLS на всех участках, шифрование на диске (Yandex KMS), аудит запросов в `OpenSearch` |

### 4.3 Политика хранения

| Параметр | Решение |
| -------- | ------- |
| Структура индексов | Отдельный Data Stream на систему (`logs-shop-api-*`, `logs-crm-api-*`, `logs-mes-api-*`, `logs-rabbitmq-*`, `logs-db-*`, `logs-s3-*`) для изоляции схем, RBAC и TTL |
| Сроки хранения (ISM) | Приложения и `RabbitMQ`: `30 дней` в `Hot` (покрывает цикл заказа > 3 недель) -> `60 дней` в архиве `S3` -> удаление. `PostgreSQL`/`S3`: `14-30 дней` в `Hot`. `DEBUG` (`logs-debug-*`): `3-7 дней`. Аудит безопасности: `180 дней` |
| Объем и лимиты | ~`2-5 КБ`/запись -> `0.5-1.5 ГБ/сутки` (`30-90 ГБ` за 30 дней с 1 репликой); кластер `200-300 ГБ` с запасом x3. Rollover шарда по `25 ГБ` или `7 дней`; `rate limit` в `Fluent Bit`/`Logstash` от переполнения при лавине ошибок |

### 4.4 Анализ логов: алертинг и поиск аномалий

| Механизм | Сценарии | Действие |
| -------- | -------- | -------- |
| `OpenSearch Alerting` | Всплеск `ERROR`/5xx (> 10 за 5 мин или > 1%); сообщения в DLQ `RabbitMQ`; ошибки БД/`S3`/3D-расчета; зависание заказов сверх SLA; всплеск 401/403 на B2B API | Алерт в Slack/Telegram дежурному инженеру, в поддержку или ИБ по приоритету |
| `OpenSearch Anomaly Detection` (RCF) | Резкий всплеск создания заказов или 3D-расчетов (например, 4 -> 10 000 записей/с при DDoS конкурентов или зацикливании B2B-клиента) | Немедленный алерт в DevOps/ИБ, включение правил WAF / rate-limiting и блокировка источника |
| `OpenSearch Anomaly Detection` (RCF) | Падение потока бизнес-событий до 0 в рабочие часы ("тишина"); сдвиг длительности 3D-расчетов и SQL вверх | Проактивный алерт о скрытом отказе интеграции или деградации `MES`/`БД` до массовых таймаутов |
