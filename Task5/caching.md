# Архитектурное решение по кешированию

## 1. Мотивация

Операторы жалуются на медленную загрузку дашборда `MES`, а клиенты - на скорость выполнения заказов. Частые чтения списка заказов конкурируют за ресурсы `MES DB` и `MES API` с расчетами 3D-моделей (2-30 мин). Кеширование разгрузит `MES DB`, ускорит отклик дашборда до миллисекунд и исключит повторные расчеты одинаковых моделей.

| Элемент (`MES API`) | Ключ кеша | Зачем кешировать |
| ------------------- | --------- | ---------------- |
| Список заказов дашборда (фильтры, пагинация) | `orders:list:v{N}:{filter_hash}` | Многократные одинаковые чтения первой страницы всеми операторами; главный источник нагрузки на `MES DB` |
| Карточка заказа | `order:{order_id}` | Повторные открытия деталей заказа при работе оператора |
| Расчет стоимости 3D-модели | `price:v{F}:{model_sha256}:{params_hash}` | Исключает повторный 2-30-минутный пересчет типовых и повторных 3D-моделей |

Операции записи статусов и очередь `RabbitMQ` не кешируются - источником истины остается `MES DB`.

---

## 2. Предлагаемое решение

### 2.1 Серверное vs клиентское кеширование

Выбирается **серверное распределенное кеширование** (`Managed Service for Valkey / Redis` в Yandex Cloud, клиент `StackExchange.Redis` в `MES API`):

- **Почему серверное:** операторы работают с общим списком заказов. Браузерный кеш даст рассинхронизацию (два оператора увидят один заказ свободным) и не снизит нагрузку на `MES DB` с разных рабочих мест.
- **Где остается клиентское:** только HTTP-кеш (`Cache-Control`, `ETag`) для статики `MES UI` (`JS`, `CSS`).
- **Почему `Redis`, а не локальный in-memory кеш:** сохраняется при рестартах `MES API` и готов к горизонтальному масштабированию сервиса без расхождения копий.

### 2.2 Паттерн серверного кеширования

Выбирается **`Cache-Aside` (Lazy Loading)**.

| Паттерн | Выбор | Обоснование |
| ------- | ----- | ----------- |
| `Cache-Aside` | Да | Кешируются только реально открываемые фильтры и страницы; простая реализация для одного C#-разработчика в `MES`; отказоустойчивость через fallback на `MES DB` |
| `Write-Through` | Нет | При смене статуса одного заказа пришлось бы пересчитывать все комбинации фильтров и страниц списка; замедляет запись (`MES DB` + `Redis`) и хранит нечитаемые данные |
| `Refresh-Ahead` | Нет | Невозможно заранее предсказать фильтры операторов; фоновый прогрев нагружает `MES DB` и усложняет код |

### 2.3 Диаграмма последовательности действий

Диаграмма чтения списка заказов и изменения статуса с участием кеша: [sequence-caching.drawio](./sequence-caching.drawio).

Участники: `Оператор`, `MES UI`, `MES API`, `Redis (Кеш)`, `MES DB`, `RabbitMQ`.

- **Чтение (`GET /orders`):** `MES API` берет список в `Redis` по текущей версии `orders:list:version` (`Cache Hit`) или читает из `MES DB` с записью в `Redis` на `120 сек` (`Cache Miss`); при недоступности `Redis` идет напрямую в `MES DB`.
- **Запись (`PATCH /orders/{id}/status`):** `MES API` обновляет статус в транзакции `MES DB`, инвалидирует кеш в `Redis`, публикует `OrderStatusChanged` в `RabbitMQ` и возвращает `200 OK`.

### 2.4 Стратегия инвалидации кеша

Выбирается **программная инвалидация по ключу/версии + страховочный `TTL`**: после каждой записи заказа в `MES DB` (из API или consumer `RabbitMQ`) выполняется `INCR orders:list:version` (сброс всех списков за `O(1)` без `SCAN`) и `DEL order:{id}`. Страховочный `TTL` (`120-300 сек`) очищает старые версии `v{N-1}` и страхует от сбоя инвалидации. Для 3D-расчетов используется `TTL 7 дней` + версия формулы `v{F}` в ключе.

| Стратегия инвалидации | Плюсы | Минусы |
| --------------------- | ----- | ------ |
| **Программная по ключу/версии + `TTL`** (выбрана) | Мгновенная актуальность списка; `O(1)` инвалидация любых фильтров через `INCR`; автоочистка по `TTL` | Нужен вызов инвалидации во всех точках записи `MES API` |
| Временная (только `TTL`) | Минимум кода | Окно устаревших данных на весь `TTL` (конфликты операторов); короткий `TTL` (5-10 с) роняет hit rate |
| Только по ключу (без `TTL`) | Мгновенный сброс известных ключей | Поиск ключей фильтров через `SCAN` нагружает `Redis`; при сбое сети устаревшие данные не очистятся |
