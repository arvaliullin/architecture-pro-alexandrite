# Архитектурное решение по трейсингу

## 1. Системы для покрытия трейсингом и точки сбоя

Покрываемые системы (выделены красной рамкой на схеме):

| Компонент | Где заказ может сломаться или зависнуть |
| --------- | --------------------------------------- |
| `Shop API` (Spring Boot) | Ошибки загрузки 3D-модели в `S3`, сбои сохранения статусов (`INITIATED` -> `SUBMITTED`) в `Shop DB`, расхождение с `CRM` |
| `CRM API` (Spring Boot) | Потеря входящего сообщения от `MES`, дублирование B2B-заказа, зависание между `SUBMITTED` и `MANUFACTURING_APPROVED` |
| `MES API` (C#) | Таймауты и повторы B2B API (`API user`), зависание расчета 3D-модели (2-30 мин), медленные запросы в `MES DB`, сбои публикации в очередь |
| `Очередь сообщений` (`RabbitMQ`) | Долгое ожидание в очереди, сбой обработки потребителем, потеря сообщений между `CRM API` и `MES API` |

Обращения к `Shop DB`, `MES DB` и `S3` фиксируются как дочерние спаны внутри `Shop API`, `CRM API` и `MES API`.

---

## 2. Данные, попадающие в трейсинг

| Категория | Поля / атрибуты | Назначение |
| --------- | --------------- | ---------- |
| Контекст | `trace_id`, `span_id`, `parent_span_id` (W3C Trace Context) | Связывание вызовов между сервисами и очередью |
| Заказ | `order_id`, `channel` (`b2c`, `b2b`), `partner_id`, `status_from`, `status_to` | Поиск пути конкретного заказа и места зависания |
| Вызов | `service.name`, `operation` (HTTP, SQL, `S3`, очередь), `duration_ms`, `http.status_code`, `error`, `error.message` | Выявление ошибок и разложение задержек |
| Очередь и 3D | `mq.queue`, `mq.routing_key`, `mq.message_id`, `model.size_bytes`, `model.polygons` | Поиск потерянных сообщений и связь сложности 3D со временем расчета |

ПДн (ФИО, контакты, адреса), секреты, токены и содержимое 3D-файлов в трейсы не попадают.

## 3. Мотивация

Метрики показывают проблему на уровне сервиса, а трейсинг показывает, на каком шаге пропал или завис конкретный заказ.

| Метрика | Тип | Ожидаемый эффект |
| ------- | --- | ---------------- |
| MTTR по инцидентам с заказами | Техническая | Поиск причины сбоя или пропажи заказа за минуты вместо часов/дней |
| Время локализации узких мест в `MES API` | Техническая | Разделение задержки на `MES DB`, `S3`, расчет 3D и очередь |
| Доля просроченных (> 3 недель) и потерянных заказов | Бизнес | Снижение срывов сроков за счет быстрого устранения точек обрыва |
| Время ответа клиентам B2C и партнерам B2B | Бизнес | Точный статус заказа в поддержке и снижение оттока B2B-контрактов |

## 4. Предлагаемое решение

| Компонент | Технология | Роль и доработки |
| --------- | ---------- | ---------------- |
| Инструментация | `OpenTelemetry SDK` (Java для `Shop API`/`CRM API`, .NET для `MES API`) | Автоинструментация HTTP, PostgreSQL, `S3`, `RabbitMQ` + бизнес-спаны с `order_id` и сменой статуса |
| Сборщик | `OpenTelemetry Collector` | Прием OTLP/gRPC (TLS), фильтрация ПДн, батчинг, tail-based sampling (100% ошибок и долгих операций + сэмплинг успешных) |
| Бэкенд и UI | `Jaeger` | Поиск по `trace_id`/`order_id` и просмотр цепочек вызовов |
| Хранилище | `Managed OpenSearch` (Yandex Cloud) | Хранение спанов и индексов с TTL 14-30 дней |

Контекст (`traceparent`) пробрасывается в HTTP и заголовках `RabbitMQ`. Между `Shop API` и `CRM API` (пока оба работают через `Shop DB`) в записи заказа сохраняются `order_id` и `trace_id` для связывания через `order_id` и Span Links.

Схема C4 с новыми компонентами и связями (выделены красным): [c4-tracing.drawio](./c4-tracing.drawio).

## 5. Компромиссы

- **Общая `Shop DB`.** `Shop API` и `CRM API` не общаются по сети - автоматический проброс `traceparent` невозможен до перехода на очередь; нужна корреляция через `order_id` и запись `trace_id` в БД.
- **Долгий цикл заказа.** Обработка длится дни и недели, поэтому один трейс не покрывает весь путь от `INITIATED` до `CLOSED` - история собирается выборкой по `order_id`.
- **Внешние границы.** Внешние `API user` и транспортная компания (`CLOSED`) не передают внутренний контекст.
- **Накладные расходы и ресурс команды.** Сбор 100% спанов дорог по CPU и диску (нужен sampling), а глубокая ручная инструментация `MES API` ограничена одним C#-разработчиком (начинать с автоинструментации и ключевых точек).
- **Только диагностика.** Трейсинг ускоряет поиск сбоев, но не устраняет потерю сообщений и перегрузку `MES`.

## 6. Аспекты безопасности

| Контур | Мера защиты |
| ------ | ----------- |
| Периметр | `OpenTelemetry Collector`, `Jaeger` и `OpenSearch` только во внутренней сети; доступ в `Jaeger UI` только через корпоративный VPN |
| Внешний трафик | Заголовки `traceparent` от `Customer` и `API user` игнорируются на входе; новый корневой `trace_id` создается в `Shop API` и `MES API` |
| Внутренний доступ | Вход в `Jaeger UI` через корпоративный SSO/OIDC и RBAC (`Поддержка` - только просмотр по `order_id`, `Разработка`/`DevOps` - расширенный доступ), аудит обращений |
| Данные в спанах | Запрет записи ПДн, секретов, токенов и 3D-файлов + фильтрация/маскирование в `OpenTelemetry Collector` |
| Транспорт и хранение | TLS для OTLP и хранилища; автоматическая очистка по TTL (14-30 дней) |
